-----------------------------------------------------------------------
WHAT WE ARE MEASURING
-----------------------------------------------------------------------
Every benchmark was run twice. Once with OIR off to get the baseline
and once with OIR on. The key metric is IPC (instructions per cycle).
If OIR slows the processor down, IPC drops. It never did.

We also track how many empty slots were available, how many got filled
with replicas, and how many comparisons were done at commit.

-----------------------------------------------------------------------
KEY FINDINGS
-----------------------------------------------------------------------
1. Zero overhead across all 4 benchmarks. OIR never hurt performance
   on any workload we tested. This is because we only use issue slots
   that were going to be empty regardless.

2. Coverage ranges from 57% to 88%. The lower coverage on qsort is
   because it has more memory instructions and branches which we
   intentionally skip. Memory ops cannot be safely duplicated because
   they have side effects. Branches are skipped for the same reason.

3. Susan has the highest IPC (2.02) but still had 53 million empty
   slots. Even a highly utilized processor wastes issue bandwidth.

4. qsort has the lowest IPC (0.81) because it stalls often waiting
   for memory. Those stalls create more empty slots but also fewer
   eligible ALU candidates to fill them with, hence the lower coverage.

5. The FAULTLESS paper reported 32 to 79% overhead on real hardware.
   We see 0% in simulation. The difference is expected. In hardware
   you need actual extra pipeline entries to hold a replica as an
   independent instruction. In our simulation the replica is a flag
   on the original instruction object. The comparison logic itself
   is what we are modeling, and that is cheap.
